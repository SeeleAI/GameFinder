# “开发 Mod”Skill 经验候选列表

整理日期：2026-07-25

## 用途

本文固定从以下四个 Mod 开发样本中提炼出的可复用经验，作为后续构建“开发 Mod”Skill 的输入材料：

- GTA V AutoDriver：ScriptHookVDotNet、C#、手改 IL。
- Red Dead Redemption 2 AutoDriver：ScriptHookRDR2、C++ `.asi`。
- The Witcher 3 AutoDriver：WitcherScript。
- Cyberpunk 2077 AutoDirector：CET Lua，并预留 redscript、Codeware 和 RED4ext 路线。

本文是研究材料，不是最终 `SKILL.md`。后续应继续压缩通用流程，并将游戏、加载器和 API 特例移入按需加载的 reference。

## 证据边界

- GTA V 仓库有 58 次提交。部分交接文档后部仍保留已经淘汰的测试建议，因此必须用当前代码和最新提交交叉验证文档。
- RDR2 仓库有 20 次提交，但当前大量源码和研究文档尚未纳入 Git。Git 历史只完整覆盖早期阶段。
- The Witcher 3 仓库有 22 次提交，能够较完整地反映从接口研究、编译失败到运行时实验的迭代。
- Cyberpunk 2077 仓库尚无提交。当前只能依赖源码版本号、代码实现和文档中的版本记录，不能视为正式 Git 开发历史。

## 建议纳入 Skill 的经验

### 1. 先盘点运行环境，再决定技术路线

检查游戏版本、加载器、SDK、编译器、已安装框架、日志位置和热重载能力。先证明目标环境能够加载预期产物，再开始迁移或实现功能。

### 2. 分离行为概念、API 绑定和游戏数据

将随机行走、卡住恢复、定时传送等行为概念与具体加载器 API、游戏实体类型、模型名、坐标和 native 参数分开。跨游戏迁移时复用行为设计，重新实现绑定层，并重新采集目标游戏的数据。

### 3. 从迭代最快、风险最低的技术层开始

优先使用能够快速热重载、注册热键和输出日志的脚本层验证能力。只有当稳定生命周期、类型安全或底层接口确实需要时，才逐步迁移到正式脚本层或原生插件层。

### 4. 将源码仓库与游戏运行目录分离

将 `src/`、`docs/`、`scripts/` 和 `dist/` 放在独立仓库，通过部署脚本同步到游戏目录。避免将游戏更新、缓存、日志、第三方依赖和运行时产物混入源码历史。

### 5. 优先研究本地已验证实现

按以下顺序寻找接口和实现参考：

1. 游戏原生脚本或 SDK。
2. 本机已安装并运行正常的成熟 Mod。
3. 反编译结果、RTTI、NativeDB 或类型转储。
4. 官方和社区文档。
5. 最后才根据函数名或类型名提出假设。

### 6. 验证 API 的声明者、接收者和生命周期

不能只确认函数名和参数。必须检查声明类、接收者类型、继承链、回调所有者、返回类型、latent/异步行为以及对象在世界切换或实体重建后的生命周期。

### 7. 为未知能力建立接口矩阵

至少记录：

- 候选接口和来源。
- 函数签名或字段。
- 预期接收者。
- 已验证事实与尚未验证的假设。
- 可见成功、静默无效、脚本异常或原生崩溃。
- 备选路线和下一步实验。

### 8. 使用分级、可逆的探针顺序

按以下顺序推进危险或未知操作：

1. 只读枚举和日志。
2. 单对象、单槽位或单实体的可恢复修改。
3. 完整功能。
4. 执行后读回验证。
5. 失败时回滚。

### 9. 一个实验只回答一个主要问题

使用独立热键、模式、参数组或 feature flag 测试单个 native、单个接收者或一个参数区间。避免一次修改同时更换任务、目标选择、速度、镜头和传送逻辑。

### 10. 长时间行为必须使用显式状态机

不要将复杂行为堆在单个 Tick 中。为准备、活动、冷却、传送、替换、验证和恢复设置显式状态，例如：

```text
Idle
-> Prepare
-> Active
-> Cooldown
-> Teleport
-> Replace
-> Verify
-> Recovery
```

### 11. 在任务或阶段切换时设置静默窗口

先停止或清除旧任务，等待引擎释放任务状态，再进行传送、换车、换模或重新入座，最后重新下发任务。不要假设清零速度、刹车或立即覆盖坐标能够替代任务状态切换。

### 12. Watchdog 必须检查真实世界进度

不能只检查目标是否存在或经过了多少时间。应跟踪实际位置、2D 位移、速度、目标距离和最后进展时间，并在无进展时取消旧任务、重新规划或进入恢复状态。

### 13. 区分一次性命令、短期请求和持久状态

接口调用成功不代表效果会持续。引擎 AI、玩家控制器或任务系统可能很快覆盖它。根据接口性质选择：

- 在任务重新下发后再次应用。
- 周期性重申。
- 使用 heartbeat。
- 改用真正持久的行为接口。

### 14. 不要将实体句柄或语言包装对象视为永久身份

换模、世界加载、重生、上下载具和脚本重载后重新获取玩家及相关实体。优先使用稳定的 EntityID、handle hash 或游戏提供的身份字段验证对象是否仍是原实体。

### 15. 结构性修改采用事务模式

按以下顺序执行换模、换车、换马、换武器和类似操作：

```text
保存旧状态
-> 创建新对象
-> 验证新对象
-> 切换所有权
-> 清理受控旧对象
```

不要在新对象确认可用之前销毁旧对象。

### 16. 只清理 Mod 自己拥有的资源

为生成实体、临时物品、附加能力、相机、敌人和测试载具维护 ownership 标记。不得自动删除玩家原有物品、剧情坐骑、持久实体或其他 Mod 建立的状态。

### 17. 使用分阶段传送安全管线

传送流程应优先包含：

1. 使用官方传送点或已验证锚点。
2. 请求目标区域 streaming 和 collision。
3. 执行 navmesh 或 safe-spot 检查。
4. 校正地面 Z。
5. 限制垂直差并排除无效向量。
6. 根据坐骑、载具和世界切换状态选择传送方式。
7. 传送后验证实际位置。
8. 有限重试。
9. 失败时停在安全锚点，不执行盲目坐标写入。

### 18. 建立运行时拒绝标记和永久黑名单

允许测试者在游戏中标记坏目标，并输出机器可搜索的记录、坐标和原因。将反复失败的目标从日志提升为源码级黑名单，同时保留手动复测入口。

### 19. 所有重试都必须有边界、退路和停止条件

为重试设置最大次数、最大时间、fallback、rollback 和最终停止状态。避免每帧无限强制纠正，防止 Mod 与引擎状态持续争夺控制权。

### 20. 为未知底层调用提供 Safe Mode

如果某个 RTTI 对象、quest 参数、native payload 或函数指针可能引发原生崩溃，先只构造、检查和记录对象，不直接发送危险调用。确认对象类型和包装方式后再进入真实执行模式。

### 21. 围绕诊断问题设计结构化日志

日志至少应覆盖：

- 当前模式、状态和阶段。
- 游戏时间、阶段开始时间和冷却状态。
- 玩家及实体稳定 ID。
- 目标坐标和实际坐标。
- 调用的接口、事件或任务类型。
- 重试次数和 fallback。
- 拒绝、取消、失败与回滚原因。

在输入回调的第一步写日志，以区分热键或输入绑定失败与游戏 API 失败。

### 22. 提供统一的 Stop、Abort 和 Shutdown 清理路径

停止时取消任务、恢复输入、相机、通缉或保护状态，释放生成实体，回滚未完成事务，并注销加载器回调或事件监听。不能只设置一个 `mode = false`。

### 23. 建立构建、部署和验证闭环

所有技术栈都应遵循“验证成功后才部署”。针对反编译或二进制补丁工作流，执行：

```text
反编译
-> 修改
-> 重新构建或汇编
-> 静态加载检查
-> 部署
-> 再反编译或 hash 核对
-> 运行时日志验证
```

明确记录是否支持热重载，以及哪些产物更换后必须重启游戏。

### 24. 将失败实验作为一等资料保存

记录失败接口、参数、测试环境、观察结果、为何放弃和替代方向。不要只保存最终成功代码，否则后续开发者会重复测试同一条无效路径。

### 25. 分离稳定路径和实验路径

不要直接用未经验证的实验覆盖稳定功能。使用独立热键、模式、备份文档或 feature flag 隔离实验，验证通过后再合并到稳定状态机。

### 26. 将相似现象拆成正交问题

分别诊断输入绑定、资源加载、脚本编译、实体状态、AI 行为、镜头控制、视觉覆盖和底层补丁。不要因为两个问题产生相似画面，就假设它们由同一机制控制。

### 27. 让随机化可测试、可复现并能够收敛

使用加权池、无放回选择、避免立即重复、记录随机结果，并结合运行时拒绝列表和永久黑名单。避免无约束随机坐标、模型或数据记录。

### 28. 在文档中区分事实、假设、失败路径和当前实现

每个实验记录至少标注：

- `Confirmed`：已在游戏中验证。
- `Hypothesis`：尚未验证。
- `Known-bad`：已经失败或具有已知危险。
- `Current implementation`：当前代码的真实行为。

每轮修改后检查文档是否仍与当前代码和最新提交一致。

## 不应进入 Skill 核心的内容

以下内容应放入按游戏或技术栈加载的 reference，不应写成通用规则：

- native hash、固定签名和未知参数。
- 固定游戏路径、SDK 版本和 Visual Studio toolset。
- 热键编号。
- 具体模型名、武器名和坐标数据。
- 某次实验的固定秒数、距离和速度阈值。
- GTA V、RDR2、The Witcher 3 或 Cyberpunk 2077 专属目录结构。
- 游戏本体、第三方加载器 DLL、用户存档和大型运行时数据。

## 后续 Skill 分层建议

后续构建 Skill 时：

- 将本列表中的通用决策流程和安全约束压缩进 `SKILL.md`。
- 将接口研究方法整理为一个 reference。
- 将长时间状态机、watchdog、传送和恢复模式整理为一个 reference。
- 将事务、ownership、回滚和清理模式整理为一个 reference。
- 将构建、部署、热重载和验证闭环整理为一个 reference。
- 将四个游戏的 API、加载器、目录和实验结论放入按游戏加载的 reference。
- 只在重复执行且需要确定性时增加脚本，不为一次性说明创建脚本或模板。
